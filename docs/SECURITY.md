# Security baseline — release blocker

Required chain: Agent -> unique identity -> least privilege -> sandbox -> action log -> policy gate -> human approval -> rollback.

1. Default READ-ONLY / DENY-BY-DEFAULT: status/audit/watch do not change configuration.
2. Device identity/credential unique per endpoint; service permissions restricted.
3. No API keys, private keys, tokens or user secrets in code, command output, logs or prompts.
4. Validate every input, output schema, policy and executable; fail closed on uncertainty.
5. Remote execution never offers arbitrary shell or scripts; typed allowlisted operations only.
6. Scan, configuration write, delete, deploy, admin and firewall changes require explicit human approval and auditable intent.
7. Isolation/sandbox, blast-radius limit, dry-run, canary, kill switch and rollback before side-effects.
8. Keep last known valid local security posture when disconnected; no remote fail-open.
9. Protect audit logs against modification; redact sensitive fields and log decisions.
10. Public GitHub: no internal IPs, private topology, credentials, proprietary payloads or production configuration.
11. CI compile/test only; never auto-deploy production.

## Approval gate for `scan --quick` (MVP-3)
`scan` is the only side effect. Controls (details in [CLI.md](CLI.md)):
- **Gate first:** Defender must be the primary engine (`AMRunningMode` == `Normal`); anything unknown is refused (fail closed) and nothing is prompted.
- **Human approval on a real console:** exact phrase typed at a prompt; stdin must be a console input handle and stderr a console. Pipes, files, `NUL`, closed handles, EOF, read errors and wrong text are all refusals. No bypass flag exists. Any future automation switch is a separate, human-approved decision.
- **Recorded actor:** the Windows account and UTC time of approval are part of the output; shared evidence must redact them.
- **Re-check before acting:** the gate is evaluated again after approval, immediately before `Start`.
- **Minimal scope:** one quick scan; no path argument, no full/custom scan, no remediation, quarantine or configuration change; no network.
- **Honest outcome:** success is claimed only when Defender's own timestamps show a new completed scan; access denied, errors, timeout and Ctrl+C are reported as such. The tool cannot cancel a scan it started.
- **Not a boundary against same-user code:** a process already running as the user can call the same WMI method; the gate defends against accidental and scripted invocation of *this tool*, not against malware with the user's rights.

## Background service (MVP-4)
The service is optional and read-only: it runs the same observation as `watch` and stores small change events.
- **Install/uninstall are approved changes:** `service install` / `service uninstall` need the exact phrase `INSTALL SERVICE` / `UNINSTALL SERVICE` typed on a real console (same state machine as the scan approval, `evaluate_approval(in, phrase)`), plus Administrator rights; `--dry-run` only checks. Refused = exit 4.
- **Read-only IPC:** the pipe protocol has exactly three verbs (`STATUS`, `HEALTH`, `EVENTS [n]`); requests are one ASCII line of at most 128 bytes, strictly parsed, never echoed back; replies are capped at 256 KiB and validated by the client. A unit test pins the verb allowlist, so adding a write/scan/policy verb is a visible, reviewed change. Pipe ACL and server identity checks belong to the Windows layer.
- **Store:** parameterized SQL only, `trusted_schema=OFF`, defensive mode, extension loading compiled out, `synchronous=FULL`. No file content or secrets are stored; every field is truncated. Bounded by rows and bytes (oldest rows rotate out); a database written by a newer version is refused (fail closed); a corrupt file is a clean error, never a crash or silent data loss.
- **Same binary, one hardening profile:** the service is `meta-sec.exe service run --scm` (the SCM passes those arguments; `service run --console` is the foreground twin). Both modes restrict DLL search to System32 first (`SetDllDirectoryW(L"")` + `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`); `wscapi.dll` is already loaded with `LOAD_LIBRARY_SEARCH_SYSTEM32`.
- **Install refuses an unsafe binary location, before any prompt:** the registered binary must be inside `%ProgramFiles%`, `%ProgramFiles(x86)%` or `%SystemRoot%` (known-folder API), a plain absolute drive path (no UNC, `..`, quotes, `%`, `&`, `;`, ADS...), ending in `.exe`, AND neither the file nor any directory down to that root may grant write/delete/change-permissions to anyone but SYSTEM, Administrators and TrustedInstaller (so `C:\Windows\Temp` is refused although it lies under `%SystemRoot%`). A user-writable binary run as a service would be a privilege escalation. The `ImagePath` is always quoted. Gate order: elevated -> path -> service exists -> `--dry-run` stops -> typed approval -> re-check all -> create. A build directory can therefore never reach `CreateService` (tested: `cli_service_install_*`, `service_install_unit` sweeps 2304 gate combinations).
- **Service account and configuration:** `NT AUTHORITY\LocalService`, service SID type UNRESTRICTED (`NT SERVICE\MetaSecAgent` is used in ACLs), required privileges = `SeChangeNotifyPrivilege` only, start AUTO + delayed, failure actions restart after 60 s / 60 s / 5 min (reset 1 day, also on non-crash failures), preshutdown 30 s. **Unmeasured (no Administrator on the development machine):** whether LocalService can read Defender (`ROOT\Microsoft\Windows\Defender`) and the firewall policy. If `service status` then shows `service_overall` INCOMPLETE / UNKNOWN checks, the documented fallback is `sc config MetaSecAgent obj= LocalSystem` (the ACLs use the service SID, so they keep working).
- **Data directory `%ProgramData%\MetaSecAgent`** (SHGetKnownFolderPath, not environment variables), created by the elevated installer with protected DACL `D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;0x1301bf;;;<S-1-5-80-...service SID>)`: SYSTEM and Administrators full, the service Modify, inheritable, nothing inherited, no access for ordinary users (the CLI reads events only through the pipe). Check with `icacls "%ProgramData%\MetaSecAgent"`. On every start the service re-applies the DACL (when it may) and verifies it: protected, no allow-ACE for any other account, the directory (and its path) not a reparse point, owner SYSTEM / Administrators / the service / the running account. Any failure = fail closed: the store is not opened, the service keeps observing and keeps the pipe, and `service status` shows `store_errors` and the reason in `last_error` (no crash loop). `--console` without `--data-dir` uses `%LOCALAPPDATA%\MetaSecAgent-dev` (current user + SYSTEM + Administrators only) and never touches ProgramData.
- **Named pipe `\.\pipe\MetaSecAgent`:** byte mode, overlapped, `PIPE_REJECT_REMOTE_CLIENTS`, first instance created with `FILE_FLAG_FIRST_PIPE_INSTANCE` (a squatted name is reported and the service keeps observing), at most 4 instances with one worker each (no thread or memory growth), 4 KiB buffers. DACL+label `D:P(D;;GA;;;NU)(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x120083;;;IU)(A;;GA;;;<server SID>)S:(ML;;NW;;;ME)`: network logons denied, interactive users get read+write+read-attributes but NOT `FILE_CREATE_PIPE_INSTANCE`, the server's own service SID gets full control (needed to create its further instances), medium-integrity no-write-up label; nothing for Everyone/Anonymous. Every connection: 2 s read deadline, reply write and drain bounded, all waits also wait on the stop event, so a silent, slow or oversize client occupies one instance for at most a few seconds and can never block the observer or the stop path.
- **Client trusts the service, not whoever owns the name:** the CLI connects with `SECURITY_IDENTIFICATION`; for the default pipe name it requires `GetNamedPipeServerProcessId` == the process id the SCM reports for `MetaSecAgent` (a user process that squatted the name yields `INVALID_REPLY` / `PIPE_SERVER_NOT_SERVICE`). The SCM process id is used instead of opening the server's token because a standard user cannot open a service process token. `--pipe-name` overrides (foreground/tests) skip this check.
- **Uninstall:** stops the service (30 s bound; not removed if it will not stop), deletes it, and deliberately leaves the data directory: stored events are evidence, the operator removes them.
- **Who can read status and events:** every INTERACTIVE local user (the `IU` ACE) can read `STATUS`/`HEALTH`/`EVENTS` through the pipe, not only administrators; non-interactive logons (services, batch, scheduled tasks as other accounts) and all network logons are denied. The data is small redacted facts (check ids, states, times), no secrets, but it is not confidential from local interactive users.
- **Accepted risk, local denial of service on the pipe:** any interactive user can open the pipe and hold instances. Mitigations: the whole request line must arrive within 500 ms (250 ms on the one reserved instance, so an instance recycles within a fraction of a second), the wait for the client to close is bounded the same way, replies are bounded to 2 s x 2, there are a fixed 4 instances, and the observer and stop path never wait on a client. Residual: a persistent local attacker can keep `service status` flaky; it cannot stop the observer, corrupt data or run anything. Accepted for a local, read-only, same-machine channel.
- **Service-mode data directory ownership:** a pre-existing `%ProgramData%\MetaSecAgent` must be owned by SYSTEM, Administrators or the service SID (never merely the running account); it may only contain plain files (no sub-directory, reparse point or hard link) owned by those accounts or the service account, otherwise the store is refused (degraded, explained in `service status`). UNC, device (`\\.\`, `\\?\`) and `..` paths are refused for `--data-dir`.
- **Install/uninstall leave a record:** after the change is attempted, one entry (action, actor, result code) is written best-effort to the Windows Event Log (Application, source `MetaSecAgent`, event id 1000); the report says whether it was recorded (`audit_recorded`, never faked: a failed write does not change the outcome, it is shown as a warning). The approval prompt shows the full ImagePath and account (install) or the registered ones (uninstall). A missing location check in the Windows layer refuses the install (fail closed).
- **Known limitations (found in review, not fixed in MVP-4):** (L1) the client checks the pipe server only by process id, sampled before it connects; a process id could in theory be recycled between the check and the exchange, so the identity check narrows but does not eliminate squatting; the reply is still strictly validated and only read-only data flows. (L4) the install-path ACL walk checks who may write a directory but ignores object owners; an owner can always change an ACL, so a directory owned by a non-admin account inside an admin-only parent is not detected. (Residual) a legitimate client can be dropped by the 250 ms reserved-instance deadline on a loaded machine; the CLI does not retry.
- **Failures are visible:** store failures are counted and exposed (`store_errors`, `last_error` in `service status`), not swallowed.
- **Not a boundary against same-user/admin code:** an administrator can stop the service or edit its database; the log is not tamper-proof (it is local evidence, not an audit trail against the machine owner).
